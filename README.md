# ТЗ Практикум

Учебный веб-сервис: студент в роли инженера по автоматизации переписывается с заказчиком, выясняет требования и составляет техническое задание на систему автоматического управления.

Сервис работает целиком в браузере. Нет регистрации, базы данных, сервера, внешних API и языковых моделей. Ответы заказчика формирует локальный сценарный движок, а результаты рассчитываются на устройстве студента и никуда не отправляются.

## Запуск

Нужен Node.js 20 или новее.

```bash
npm install
```

```bash
npm run dev
```

| Команда | Что делает |
|---|---|
| `npm run dev` | Режим разработки |
| `npm run build` | Проверка типов (vue-tsc) и сборка в `dist/` |
| `npm run preview` | Просмотр собранной версии |
| `npm run test` | Unit-тесты (Vitest) |
| `npm run typecheck` | Проверка типов |
| `npm run test:e2e` | Браузерные сценарии (Playwright). Перед первым запуском: `npx playwright install chromium` |
| `npm run docs` | Обновляет `docs/intents.md` и `docs/example-result.md` |
| `npm run screenshots` | Снимает экраны на семи ширинах (320–1920 px) и проверяет консоль и обрезанный текст (нужен запущенный `vite preview` на порту 4173) |

После `npm install` интернет не требуется. Папка `dist/` работает на любом статическом хостинге, в том числе из подкаталога по пути `/tz-praktik/` (`base` в `vite.config.ts`; маршрутизация hash-историей, серверный fallback не нужен).

## Оформление

Каркас на Dashboard-компонентах Nuxt UI (`UDashboardGroup`, `UDashboardSidebar`, `UDashboardPanel`, `UDashboardNavbar`), как в общем слое `@admsr/ui`. Свои цвета и скругления не заданы: всё берётся из токенов Nuxt UI. Тема (11 готовых) и режим светлый / тёмный переключаются в меню студента в левом нижнем углу, выбор хранится в `localStorage`. По умолчанию — тёмная тема emerald + slate.

## Что умеет сервис

- **Старт.** Описание упражнения, кейс, время, число тем, имя студента. Режим один — учебный.
- **Диалог.** Свободный текст, индикатор набора, уточнение конкретного ответа, повтор вопроса, фиксация ответа как требования с правкой формулировки. Под каждым ответом заказчика — оценка «подходит / не подходит» с необязательной причиной в модальном окне; оценки попадают в файл прогресса, `result.json` и историю переписки в `result.md`.
- **Реестр.** 13 категорий, источник и время, отметки «требует уточнения» и «противоречие», фильтры, ручное добавление, правка, смена категории, удаление, объединение.
- **Редактор ТЗ.** 13 разделов, перенос записей из реестра с последующей правкой своими словами. Готовый текст сервис не генерирует.
- **Результат.** Балл, полнота диалога и ТЗ, пропуски, противоречия, полезные и слишком общие вопросы, рекомендации, переписка, текст ТЗ и эталон, открытый только после завершения.
- **Файлы.** `result.md`, `result.txt`, `result.json`, печать, файл прогресса с загрузкой обратно. Автосохранение в `localStorage` и восстановление после перезагрузки.

Публичная версия работает **только в учебном режиме**: прогресс по темам, список направлений без готовых вопросов, подсказки по разделам и качеству вопросов. Старые попытки в режимах «стандартный» и «строгий» загружаются без потерь и продолжаются с прежними правилами ответов заказчика (интерфейс при этом учебный); завершённые остаются как были.

## Как работает сценарный движок

`respond(state, input, scenario)` — чистая функция: новое состояние и ответ зависят только от входных данных. Поэтому попытку можно восстановить из файла, а одинаковый seed воспроизводит те же реплики.

1. **Нормализация.** Нижний регистр, `ё → е`, десятичная запятая, единицы (`°С`, `градусов → градц`, `м³/ч`, `кубов в час → м3ч`, `бар` и `кПа` пересчитываются в МПа), диапазоны, основы слов.
2. **Понятия.** Слова превращаются в понятия по словарю `lexicon`: `давлен`, `=мпа` → `press`. Прощается опечатка в длинной основе. Фраза-место отменяет предмет: «после теплообменника» не делает вопрос вопросом о теплообменнике (`conceptSuppress`).
3. **Контекст.** Если в вопросе нет своего предмета, он берётся из текущей темы: «какое отклонение?» после разговора о температуре. Короткое уточнение наследует признак предыдущего вопроса на один ход. Хотя бы один признак должен быть в самом вопросе, иначе бессмыслица получила бы ответ по теме.
4. **Сверка чисел.** Если студент утверждает значение, движок сравнивает его с фактом: подтверждает, поправляет или указывает на путаницу («70 — это предупреждение»). Значение, которое ещё не называлось, заказчик не раскрывает.
5. **Неоднозначность.** «Какое давление?» без уточнения вызывает встречный вопрос. Следующая реплика («после насоса») дополняет исходный вопрос.
6. **Оценка намерений.** Обязательные группы (И из ИЛИ) дают 3 балла, через контекст 1,4; дополнительные признаки — 0,7; сходство с примерами — до 3; лишний предмет или признак снижают балл. Исключающие признаки отсекают намерение. Порог — 2,5.
7. **Раскрытие.** У намерения есть шаги, каждый открывает 1–3 факта. Факт с предпосылкой заказчик сообщает вместе с ней («рабочая 60 °C, допуск ±2 °C»): порядок вопросов угадывать не нужно; просьба «сначала уточните» остаётся лишь запасным вариантом. На непонятный вопрос заказчик в учебном режиме сам называет ещё не затронутую тему. Длинный перечень идёт порциями («что ещё?»).
8. **Повтор и настроение.** Повторный вопрос даёт короткий ответ и учитывается в оценке; просьба напомнить не штрафуется. От общих и повторных вопросов падает терпение заказчика, и это слышно в тоне.

Отдельно отмечается: уровень `specific` не раскрывается общим вопросом (проверяет тест), один ответ содержит не более трёх фактов (тоже проверяет тест).

## Формат сценария

```ts
type ScenarioFact = {
  id: string;
  category: string;                 // id из categories в scenario.ts
  value: string;                    // значение для эталона
  aliases: string[];                // признаки в тексте: 'клапан+закр+питан' — все основы в одном предложении
  disclosureLevel: 'general' | 'specific' | 'followup';
  prerequisites?: string[];         // какие факты должны быть раскрыты раньше
  customerConfidence: 'certain' | 'approximate' | 'unknown';
  requirementType: 'mandatory' | 'preference' | 'proposal';
  label: string;                    // название для результата
  askLabel?: string;                // винительный падеж: «сначала уточните …»
  section: number;                  // раздел ТЗ, 1–13
  numbers?: number[];               // значения, которые должны быть рядом с признаками
  claim?: FactClaim;                // сверка числа, которое назвал студент
  isReaction?: boolean;             // описывает реакцию системы
};

type Intent = {
  id: string;
  title: string;
  kind: 'fact' | 'unknown' | 'general' | 'meta' | 'social';
  topic: string;                    // тема из topics
  required: string[][];             // [['temp','heat'], ['warning']] — (temp ИЛИ heat) И warning
  optional?: string[];
  exclude?: string[];
  examples: string[];               // минимум один; каждый пример проверяется тестом
  weight?: number;
};

type ReplyStep = {                  // replies[intent.id] — массив шагов
  facts: string[];                  // до трёх фактов
  variants: string[];               // варианты первого ответа
  short: string[];                  // короткая форма для повтора
};
```

## Инструкция преподавателя

### Настроить ответы заказчика без кода

Панель «Ответы заказчика (тест)» убрана из публичного интерфейса. Чистый модуль `src/engine/answerPack.ts` и шаблон [docs/otvety-zakazchika.json](docs/otvety-zakazchika.json) остались для тестов и ручной работы; инструкция: [docs/instrukciya-otvety-zakazchika.md](docs/instrukciya-otvety-zakazchika.md).

### Изменить ответы заказчика

Откройте `src/data/responses.ts`, найдите намерение по его `id` и поправьте `variants` (полный ответ) и `short` (ответ на повтор). Служебные реплики собраны в объекте `meta`. В шаблонах сохраняйте подстановки `{short}`, `{given}`, `{correct}`, `{label}`, `{other}`, `{need}`, `{value}`, `{area}`.

Значение в реплике должно совпадать с фактом: сверка чисел опирается на `facts.ts`.

### Добавить новый факт

1. Добавьте запись в `src/data/facts.ts`:

```ts
fact('valve_stroke', 'actuators', 9, 'Время хода клапана', 'Не более 60 с.', ['клапан+ход'], {
  numbers: [60],
  claim: { unit: 's', values: [60], concepts: [['valve'], ['delay']], display: '60 с' },
}),
```

2. Добавьте намерение в `src/data/intents.ts` и шаг в `src/data/responses.ts`:

```ts
{ id: 'valve_stroke', title: 'Время хода клапана', required: [['valve'], ['delay']], examples: ['Какое время хода клапана?'] },
```

```ts
valve_stroke: [step(['valve_stroke'], ['Полный ход не дольше минуты.', 'Клапан должен успевать за 60 секунд.'], ['Не дольше 60 секунд.'])],
```

3. Запустите `npm run test`. Тесты сообщат, если факт недостижим, понятия нет в словаре или пример не распознаётся.

### Добавить синоним вопроса

- **Новое слово для понятия** — допишите основу в `lexicon` в `src/data/intents.ts`: `flow: ['расход', 'проток', 'пролив']`. Префикс `=` означает точное совпадение: `'=кип'`. Несколько слов через пробел — последовательность: `'до насос'`.
- **Новая формулировка намерения** — добавьте строку в `examples`. Она увеличит сходство и попадёт в автоматическую проверку.

Короткие основы (меньше шести букв) опечаток не прощают, чтобы не смешивать слова вроде «вход» и «выход».

### Изменить критерии оценки

Всё находится в `src/data/evaluation.ts`: веса `weights` (в сумме 100), штрафы `penalties` (за случай, потолок, число бесплатных случаев), шкала `gradeScale`, порог заполненности раздела, список марок `brandPatterns`, разговорные обороты `speechMarkers`. Менять `evaluationEngine.ts` для этого не нужно.

### Создать новый учебный кейс

1. Скопируйте `src/data/` в новую папку, например `src/data/boiler/`.
2. В `scenario.ts` задайте `id`, название, описание, заказчика, категории и разделы ТЗ.
3. Перепишите `facts.ts`: сначала скрытую модель объекта, с числами и уровнями раскрытия.
4. В `intents.ts` оставьте общий словарь, допишите предметную лексику, обновите `topics`, `ambiguities` и намерения. Служебные намерения (`greeting`, `followup_more` и другие) можно оставить как есть.
5. Перепишите `responses.ts` и списки в `evaluation.ts`. Условия `mixups` в `evaluationEngine.ts` сейчас проверяют пороги этого кейса; для нового кейса замените значения в них.
6. Подключите новый сценарий в `App.tsx` вместо `./data/scenario` и в тестах.
7. Запустите `npm run test`. Тесты в `src/data/scenario.test.ts` проверят объём и целостность.

Движок получает сценарий параметром и не содержит предметных данных, за исключением указанной выше функции `mixups` и ключей мета-намерений `followup_*`, `is_mandatory`, `repeat_last`.

Файл прогресса привязан к `id` кейса: загрузить попытку другого кейса нельзя.

### Опубликовать на GitHub Pages

В проект уже добавлен `.github/workflows/deploy.yml`.

1. Создайте репозиторий на GitHub и отправьте проект в ветку `main`.
2. В репозитории откройте **Settings → Pages** и выберите **Source: GitHub Actions**.
3. После следующей отправки в `main` Actions проверит типы и тесты, соберёт проект и опубликует его.

Без Actions: выполните `npm run build` и загрузите содержимое `dist/` на любой статический хостинг.

## Оценка

Сумма критериев 100 баллов минус штрафы. Оценка не зависит от числа сообщений: 40 одинаковых вопросов дают почти ноль.

| Блок | Критерии |
|---|---|
| Диалог, 38 | Охват категорий, обязательные требования, выявленные сведения, которых не знает заказчик, конкретность вопросов |
| Реестр, 12 | Обязательные требования, зафиксированные с верными значениями |
| ТЗ, 50 | 13 разделов, обязательные требования, числа с единицами, разделение предупреждения и аварии, реакция системы, формальный стиль |
| Штрафы | Повторы, постоянные общие вопросы, путаница давления до и после насоса, путаница предупреждения и аварии, модель без основания («или аналог» снимает штраф), нет реакции системы, разговорная речь в ТЗ |

Пример результата: [docs/example-result.md](docs/example-result.md). Список намерений: [docs/intents.md](docs/intents.md). Скриншоты: [docs/screenshots/](docs/screenshots/).

## Известные ограничения

- Распознавание основано на словаре и правилах, а не на понимании смысла. Необычная формулировка может не распознаться; тогда заказчик просит сказать иначе. Сложноподчинённые вопросы с несколькими темами разбираются хуже коротких.
- Числа прописью («шестьдесят градусов») не распознаются.
- Сокращение «ТО» понимается только во фразах вроде «после ТО»: само по себе оно совпадает с частым словом «то».
- Проверка ТЗ сверяет наличие сведений, чисел и признаков, но не оценивает смысл текста. Формально верный набор слов получит балл; итоговую работу стоит посмотреть преподавателю.
- Защита от списывания не предусмотрена: эталон и ответы находятся в коде страницы и доступны через инструменты разработчика. Сервис предназначен для обучения, а не для контрольной работы.
- Прогресс хранится в одном браузере. При очистке данных сайта он теряется, поэтому для переноса есть файл прогресса.
- В браузере одновременно ведётся одна попытка.
- В файл прогресса не добавляется подпись, поэтому его можно отредактировать вручную.
